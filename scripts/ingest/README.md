# Ingest pipeline (v0.5)

RSS-driven listener for new YouTube uploads from FRQNCY's tracked teachers. Drafts proposed additions for `videos.json` and `playlists.json` in a shape that's mechanical to merge. **Nothing here is wired into the live site yet** — the pipeline only writes to `scripts/ingest/output/`. Merging is a human step.

Sits architecturally between the v0 scraper at `scripts/auto-grow/video-ingest.mjs` (URL-scraper, IDs only) and the v0.2 vision in `proposals/AUTO-GROW-LOOPS-V0.md` (harness-MCP agent). v0.5 adds: RSS instead of HTML scraping, full metadata, FRQNCY-voiced blurbs, and proposal JSON that mirrors the live schema.

## What it does

The listener walks every teacher in `teachers.json`, fetches their YouTube Atom feed (no API key, no quota, no auth), and diffs against the video IDs already in `playlists.json` + `videos.json`. New uploads are enriched with duration + full description via the YouTube Data API (optional — needs `YOUTUBE_API_KEY`), then each gets a FRQNCY-voiced one-sentence blurb generated by Claude (optional — needs `ANTHROPIC_API_KEY`). The result is a dated proposal file in `scripts/ingest/output/proposals/` — a JSON delta you can merge into the live data files, plus a Markdown summary for review.

## The four scripts

| File | Job |
|---|---|
| `resolve-handles.mjs` | One-time (and on-channel-rename): fetches each playlist's channel URL, extracts the canonical `UC…` channel ID, caches them in `output/channel-ids.json`. RSS needs the ID, not the @handle. |
| `listen.mjs` | The signal layer. Fetches each teacher's Atom feed, parses the latest 15 entries, returns only the ones we don't already have. |
| `enrich.mjs` | Optional. Calls the YouTube Data API to add duration + full description per new upload. No-ops if no API key. |
| `blurb.mjs` | Optional. Generates a FRQNCY-voiced 1–2 sentence description per new upload via Claude. Falls back to the raw YouTube description if no API key. |
| `propose.mjs` | The orchestrator. Runs listen → enrich → blurb → writes a dated proposal to `output/proposals/INGEST-YYYY-MM-DD.json` + a Markdown summary. |

## Run it

First-time setup (resolve channel IDs once):

```
node scripts/ingest/resolve-handles.mjs
```

Then a full ingestion pass:

```
node scripts/ingest/propose.mjs
```

That writes:

- `scripts/ingest/output/proposals/INGEST-YYYY-MM-DD.json` — the merge-shaped delta
- `scripts/ingest/output/proposals/INGEST-YYYY-MM-DD.md` — a human-readable summary

Or run the pieces individually:

```
node scripts/ingest/listen.mjs --json    # writes output/diff.json
node scripts/ingest/enrich.mjs           # adds duration/desc in place
node scripts/ingest/blurb.mjs            # adds frqncy_desc in place
```

## Env vars

| Var | Effect |
|---|---|
| `YOUTUBE_API_KEY` | Enables duration + full-description enrichment. Free tier (10k units/day) is plenty. |
| `ANTHROPIC_API_KEY` | Enables LLM blurb generation. Otherwise blurbs fall back to trimmed raw YouTube descriptions. |
| `FRQNCY_BLURB_MODEL` | Override the Claude model. Default: `claude-haiku-4-5-20251001` (fast + cheap; ~$0.002/blurb). |

Without any env vars, the pipeline still runs — you'll just get the unenriched feed data and raw-description fallback blurbs. Useful for local dry-runs.

## The proposal shape

```json
{
  "generated_at": "2026-05-25T12:00:00Z",
  "summary": { "teachers_scanned": 16, "new_uploads": 4 },
  "teachers": [...],
  "videos_json_additions": {
    "t-osho": [{ "id": "v-osho-r16", "youtube_id": "...", "title": "...", "channel": "...", "duration": "8 min", "desc": "...", "frqncy_pick": false }]
  },
  "playlists_json_updates": {
    "pl-osho": { "video_ids": ["v-osho-r16", "v-osho-r01", "v-osho-r02", ...] }
  }
}
```

The two delta fields (`videos_json_additions` + `playlists_json_updates`) are the only things you actually merge. Everything else is metadata for the review.

## Merging (the human step)

1. Open the dated `INGEST-…md` file. Skim every blurb — rewrite anything that violates the [voice playbook](../../proposals/FRQNCY-VOICE-PLAYBOOK.md).
2. Flip `frqncy_pick: true` on any entry that qualifies as a starter teaching (Editorial Standards: independence, verifiability, voice-fit).
3. Apply `proposal.videos_json_additions` to `videos.json` — append each video to its `t-*` array.
4. Apply `proposal.playlists_json_updates` to `playlists.json` — replace the named playlist's `video_ids`.
5. `node generate-watch.js` to re-inline the data.
6. Commit, push.

## Rotation

Each teacher in `teachers.json` has a `max_videos` cap (default 20) and `rotate: true|false`. When `rotate: true` and a new upload would push the playlist past the cap, the oldest entry rolls off. The popped IDs aren't deleted from `videos.json` — they just stop appearing in the playlist. Rotation behaviour is computed and surfaced in the proposal so you can see what's being pushed out before merging.

`rotate: false` means append-only — used for `pl-money` (Hidden Secrets of Money is a finite documentary series, not an ongoing feed).

## Exclusions

To explicitly reject an upload (Shorts, off-topic streams, etc.) so it never re-surfaces, add its `youtube_id` to `teachers.json` → `excluded_video_ids`. The listener filters these out before they even reach the proposal.

## Why no auto-merge

Same reason `auto-grow` is PR-mode: editorial standards require human judgment per entry. A scraped upload is a candidate, not a decision. The voice playbook in particular can't be enforced reliably enough by an LLM to ship blurbs unreviewed — at v0.5 the LLM is a drafter, not a writer.

## Wiring to a cron (later)

A disabled-by-default workflow lives at `.github/workflows/ingest.yml`. It runs `node scripts/ingest/propose.mjs` and (optionally) opens a PR with the new proposal files. Currently `workflow_dispatch`-only — flip on the `schedule` trigger when ready.

## Cost

- **RSS listening:** $0 (no auth, no API).
- **YouTube Data API enrichment:** free tier supports ~10,000 units/day; one `videos.list` batch is 1 unit. Effectively $0.
- **LLM blurb generation:** ~$0.002/blurb on Claude Haiku 4.5. At 50 new uploads/week across all teachers, ~$0.50/month.

Total: under a dollar a month at the current teacher list.

## Failure modes worth knowing

- **Channel renames its handle.** The cached `channel_id` still works (IDs are stable). No action needed.
- **Channel deletes itself.** Feed returns 404, listener logs `feed fetch failed`, that teacher is silently skipped this run. Investigate manually if it persists.
- **YouTube changes its embedded HTML.** `resolve-handles.mjs` uses four pattern fallbacks for the channel ID; if all four break, it logs `FAILED` and falls back to whatever's cached. The Atom feed itself is contractually stable — that part won't break.
- **LLM produces voice-violating copy.** Expected at v0.5. The review pass is the gate. Track violations and tighten the system prompt iteratively.

## What's next (v0.6 ideas)

1. A `--diff-only` flag on `propose.mjs` that compares against the most recent proposal rather than re-running every time.
2. Live-broadcast detection — the same Atom feed signals livestreams via `<media:content>` attributes. Could auto-populate the new "Live" area on the watch page.
3. Move the rejection list (`excluded_video_ids`) into per-teacher arrays for clarity.
4. Per-teacher voice notes — `teacher.voice_hint` injected into the blurb prompt for tighter style match.
