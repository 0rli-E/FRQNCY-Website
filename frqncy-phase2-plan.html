02 What we're adding

Two new interfaces (Telegram approvals + Learning Agent) plus a three-layer memory system. The memory layers are the spine — without them, agents stay stateless and never compound.

The interface layer

Telegram Approval Interface

Every output from any agent surfaces to your phone as a Telegram message with two buttons: Approve and Revise. Approve = it executes for real. Revise = you type one line of feedback, which becomes a learning signal. This is the only interface you touch day-to-day.

Learning Agent

A new persona, meta-tier (sibling to FRQNCY, not in the org chart). Watches every rejection, extracts structured lessons into agent_learnings, and after enough patterns accumulate, drafts updated system prompts for affected agents — sent to you for approval before deploy. Versioned, rollback-able.

The memory layer (three tiers)

Already designed in the Memory & Learning Architecture document — restated here so the full system is in one place.

Layer 1 — Working Memory (n8n native, free, zero setup)

Short-term context within a single conversation. What was just said, what was decided, what the task is. Already handled by n8n's built-in conversation memory on every AI Agent node. Nothing to build.

Layer 2 — Long-Term Memory (Supabase pgvector, free tier)

Persists across conversations and sessions. Lessons learned, approved content, past decisions, your preferences. Stored as vector embeddings in Supabase Postgres with the pgvector extension. Every agent gets a Supabase Vector Store attached as its "Memory" sub-node in n8n — semantic search retrieves relevant past context before each invocation. Embeddings caveat: Groq does not offer embeddings; use OpenRouter's free Nomic Embed model for this one job.

Layer 3 — Context Graph (Graphiti + FalkorDB, self-hosted, free)

Understands relationships and how things change over time. Not just "we launched Instagram on April 10" but "Instagram launch was connected to the Merlin timing reading, which informed the CMO strategy, which Orli approved with one revision about tone." Powered by Graphiti — open source temporal knowledge graph by Zep (Apache 2.0), self-hosted on the same Hostinger VPS, with FalkorDB as the lightest graph backend. Has a native MCP server, so Claude and the agents can query it directly. Wait until you have 30+ days of real data before deploying — a graph with no edges is useless.

04 Data layer (Supabase + Graphiti)

Two stores. Supabase Postgres holds the operational + memory data (free tier). Graphiti runs on the Hostinger VPS for the temporal context graph (also free, deploys later).

Supabase Postgres — operational tables

TablePurposeUsed by
agent_outputs Every output any agent produces. The unit of work. All agents write here
approvals Approve/Revise events from Telegram. Joined to agent_outputs. Telegram webhook writes; Learning Agent reads
agent_memory pgvector Long-term memory per agent. Embedded lessons, approved content, your preferences. Every agent reads via Vector Store node; Learning Agent writes
agent_learnings Structured Lesson Records — what happened, root cause, lesson, pattern flag. Learning Agent writes; embedded into agent_memory
agent_versions Versioned system prompts per agent. Current = active. Old = rollback-able. Learning Agent versions; agents load at runtime
audit_log Append-only record of every agent action. For debugging + trust. Auto-written by every workflow

Graphiti — temporal context graph

ConceptWhat it isWhy it lives here, not in Postgres
entities Orli, FRQNCY, Council members, projects, campaigns, decisions, partners Graph traversal beats relational joins for "who connects to what"
relationships "Orli APPROVED Instagram strategy" / "Kali reading LED TO tone pivot" Edges with timestamps — Graphiti's native model
observations Temporal facts: "Brand voice was X until April 2026, then evolved to Y" Graphiti tracks WHEN every fact became true and changed
MCP server Native MCP endpoint Graphiti exposes — Claude and agents query directly No middleware needed, ~300ms P95 hybrid search

05 The approval loop

How any agent's output becomes either real action or learning signal.

┌─────────────┐ │ Any Agent │ writes output to agent_outputs (status=pending) └──────┬──────┘ │ ▼ ┌─────────────┐ │ FRQNCY routes│ attaches context, formats for human review └──────┬──────┘ │ ▼ ┌────────────────────────────────────────────┐ │ 📱 TELEGRAM message to Orli: │ │ │ │ From: CMO │ │ For: Tuesday's Instagram post │ │ │ │ "The frequency you're looking for is │ │ already inside you..." │ │ │ │ [ ✓ Approve ] [ ✎ Revise ] │ └──────┬─────────────────────────┬───────────┘ │ tap Approve │ tap Revise ▼ ▼ ┌─────────────┐ ┌─────────────────┐ │ EXECUTES │ │ Bot asks: │ │ for real │ │ "What to fix?" │ └──────┬──────┘ └────────┬────────┘ │ │ Orli types reason ▼ ▼ writes to: ┌─────────────────┐ approvals (✓) │ Logged to │ context_graph │ approvals + fed │ audit_log │ to Learning Agt │ └─────────────────┘

Decisions inside the loop

  • What "executes for real" means depends on output type — a social post posts, an email sends, a design concept gets archived as approved direction, a decision gets logged to the context graph as a fact.
  • Approval timeout — if you don't respond in 24h, FRQNCY pings you again. After 72h, the output is auto-shelved and logged for review.
  • Batching — at certain times of day (you set them), FRQNCY can batch 3-5 approvals into one digest instead of pinging individually. Reduces interruption load.

06 The Learning Agent

A new persona — meta-tier, sibling to FRQNCY. Its only job is making the rest of the org smarter.

What it does — two cadences

Real-time (per rejection)

  1. Triggered by webhook the moment a Revise event hits the approvals table.
  2. Reads the original output, your revision note, the agent's recent memory.
  3. Diagnoses root cause and writes a structured Lesson Record to agent_learnings.
  4. Embeds the lesson and writes it to agent_memory (pgvector) under the affected agent's namespace.
  5. Next time that agent runs, the lesson surfaces in its memory recall — the mistake doesn't repeat.

Weekly (cron, e.g. Sunday 2am)

  1. Reads agent_learnings for the past 7 days, grouped by agent.
  2. For each agent with ≥3 lessons clustering around the same pattern → flips pattern_flag.
  3. Drafts a system prompt update that bakes the pattern into the agent's identity (additive).
  4. Sends the lesson + proposed new prompt to Orli via Telegram for approval.
  5. If approved, writes the new version to agent_versions. Affected agent loads it on next run.
  6. Sends Orli a weekly reflection report — what's been learned, where each agent is improving.

What it does NOT do

  • Does not write its own prompt updates without human sign-off (configurable later).
  • Does not touch the Council prompts — those are spiritually-set, not learning-evolved.
  • Does not override Orli's explicit prior corrections — only proposes additive guidance.
  • Does not learn from a single rejection. One bad output is noise. Three of the same kind is signal.

07 The Context Graph (Graphiti)

The shared brain — but specifically, a temporal knowledge graph, not a key-value store. Powered by Graphiti, self-hosted on the same VPS as n8n.

Why Graphiti, not Supabase JSONB

Earlier drafts had this living in a Supabase JSONB column. That works for storing facts but not for understanding them. Graphiti was chosen in the original Memory & Learning Architecture document for four reasons that still hold:

  • Temporal: every entity, relationship, and fact has a timestamp. The graph knows not just WHAT is true but WHEN it became true and WHEN it changed. "Brand voice was X until April 2026, then evolved to Y after 3 revision cycles" is queryable.
  • Hybrid search: semantic (meaning) + keyword + graph traversal in one query, ~300ms P95 latency.
  • Native MCP server: Claude and the agents query Graphiti directly without wrappers — same protocol the rest of the toolchain already speaks.
  • Open source, free: Apache 2.0, by Zep. Self-hosts on the same Hostinger VPS already running n8n. Graph backend: FalkorDB (lightest option for low-resource VPS).

What lives in the graph

Entity types

person · project · feature · platform · tool · concept · decision (CEO/CMO calls) · commitment (external promises) · lesson (links to agent_learnings) · open_question (unresolved)

Relationship types (sample)

APPROVED · LED_TO · OVERRODE · BUILT_ON · DEPENDS_ON · EVOLVED_FROM · VETOED (Council edges)

What FRQNCY's graph will know over time

  • About Orli: her preferences, patterns, revision history, what she cares about most, how her thinking has evolved.
  • About the mission: key decisions, pivots, milestones, what worked, what didn't.
  • About agents: which perform best on which tasks, learning history, growth trajectory.
  • About FRQNCY's world: community members, partners, content library, brand voice evolution over time.
  • About time: what changed and when — so FRQNCY never operates on stale assumptions.

Read/write protocol for agents

Once Graphiti is deployed, every agent workflow gets a sub-flow that runs before and after the LLM call. Same pattern across all agents — built once as a reusable n8n sub-workflow.

┌──────────────────────┐ │ 1. Receive task │ └──────────┬───────────┘ │ ▼ ┌──────────────────────┐ │ 2. QUERY Graphiti │ → via MCP — "what does this agent need to know?" e.g. CMO asks: recent decisions, open commitments, current brand voice lessons └──────────┬───────────┘ │ ▼ ┌──────────────────────┐ │ 3. QUERY pgvector │ → semantic recall of past lessons + memory └──────────┬───────────┘ │ ▼ ┌──────────────────────┐ │ 4. LLM does the work │ → with graph context + pgvector hits both injected └──────────┬───────────┘ │ ▼ ┌──────────────────────┐ │ 5. WRITE to Graphiti │ → new entities, new edges, new observations └──────────┬───────────┘ │ ▼ ┌──────────────────────┐ │ 6. Send for approval │ └──────────────────────┘

When to deploy

Wait until you have 30+ days of real activity after Phase 2A and 2B are running. Graphiti needs nodes and edges to be useful — deploying it on day one means querying an empty graph. Let the approval loop generate decisions, lessons, and outputs first; then bring up Graphiti to give those facts shape and time.

Why this matters

Without this layer, the CMO doesn't know what the CEO promised yesterday. The Visual Artist doesn't know the brand voice the Marketing Specialist established last week. Every agent starts from zero.

With it, the org has a shared, queryable, time-stamped memory. Every output is informed by everything that came before. The whole becomes coherent.

Risks worth naming

Approval fatigue

If FRQNCY pings you 30 times a day, you'll stop reading. Mitigation: batching + clear severity tiers (only urgent goes through immediately).

Bad lessons

Learning Agent could over-correct ("don't ever say X") and hollow out a persona's voice. Mitigation: lessons require your sign-off; rollback is one click via agent_versions.

Empty graph problem

Deploying Graphiti before there's data to populate it = querying air. Mitigation: 2D is explicitly deferred until 30+ days of approval activity have run.

Context graph drift

If agents write contradictory facts, the graph becomes noise. Mitigation: Graphiti's temporal model timestamps every fact + tracks change; conflicts surface as open_question entities.

VPS RAM pressure

n8n + FalkorDB + Graphiti on KVM 2 may get tight at scale. Mitigation: monitor RAM during 2D rollout; upgrade to KVM 4 (~$15/mo) if sustained >80%.

VPS as single point of failure

If Hostinger goes down, the whole org is offline. Mitigation: not yet — accept for Phase 2; revisit at Phase 4 with backup VPS or migrate to a managed Kubernetes setup.

11 Compounding intelligence flywheel

What this looks like over time. Pulled directly from the Memory & Learning Architecture document — restated because it's the entire reason Phase 2 exists.

Month 1 — Stateless to remembering

Agents make mistakes you correct on Telegram. Learning Agent records them. Memory is thin but growing. You're doing more correcting than approving — that's the trough.

Month 3 — Lessons start landing

Agents incorporate past lessons via pgvector recall. Revision rate drops. You approve more on first pass. Graphiti is up; the graph has its first meaningful connections (decisions, commitments, brand voice evolution).

Month 6 — System prompt evolution

Enough signal has accumulated that the Learning Agent has proposed and you've approved real prompt updates. Each agent is meaningfully better than its v1. The graph understands FRQNCY's world deeply enough to surface non-obvious connections (Kali reading from March → led to brand pivot in April → which informed three CMO outputs since).

Month 12 — Institutional memory

The org has a genuine living memory. New tasks benefit from everything learned in the past year. Agents that were generic at launch are now deeply calibrated to FRQNCY's specific voice, mission, and your preferences. This is what "living organization" means.
