# 90-day roadmap

## TL;DR

Window: **2026-05-03 → 2026-08-01** (84 days). Closes out the existing
EXECUTION-PLAN-90D window with refreshed sequencing based on what's
shipped, what's deferred, and the four product decisions made on
2026-05-03.

Three parallel tracks:

1. **Operator unblock** (Week 1) — get migrations 002–017 applied,
   social-src built and deployed, env vars set, Privy + Stripe + GitHub
   Actions secrets wired. Until this clears, half of what's in source is
   inert in production.
2. **NRG-native depth** (Weeks 1–8) — sharpen Practice, Word Illuminator,
   member surfaces, AI HD reading length differentiation, search across
   the federated feed. The "deepen what we have" track.
3. **Onchain identity + reputation** (Weeks 3–10) — Ethos read-only
   surface, DID identity wrapper, optional content-anchor. The "make
   the architecture portable" track.

Active member acquisition starts when track 1 clears (target ~Week 2).

The deferred-but-not-killed list (Lens / Farcaster bridges, mobile,
E2EE forward secrecy, OAuth+DPoP for Bluesky) stays parked through this
window per `PROTOCOL-LESSONS-2026-05.md` and `NRG-ONCHAIN-PIVOT.md`.

## Track 2: NRG-native depth (Weeks 1–8, runs alongside Track 1)

Per the user-selected focus: "NRG-native depth". Weighted by smallest
lift × highest immediate value.

### Week 2 (May 11–17): AI HD reading length differentiation

The Word Illuminator AI worker (`functions/illuminator/word.js`) and
the broader AI surface return short summaries today regardless of
member status. Members should get a longer, deeper read.

- Add `?member=1` query param support to the worker. When set + verified
  via signed Supabase JWT, return a 5-paragraph deep version with the
  same locked schema but expanded `core_read` + `practice_invitation`
  sections.
- Wire the membership-gate helper (`assets/frqncy-member-gate.js`) into
  the illuminator widget so it sets the param automatically for active
  members.
- Voice contract: "deeper view for members" not "exclusive content".
  The non-member version must still be useful — never a stub.

### Week 3 (May 18–24): Search across the federated feed

Today search (`/social/search`) is NRG-only. The federated feed reader
v1 lets members read Bluesky in the same surface; search should match.

- Extend the existing search query to optionally include cross-posted
  Bluesky rows (those with `bluesky_uri IS NOT NULL`) — they're already
  in our DB.
- For pure Bluesky search (the user's home timeline that wasn't
  cross-posted from NRG): call `app.bsky.feed.searchPosts` against the
  authenticated agent when the user is connected. Read-only — clicking
  through to bsky.app.
- "Search NRG" / "Search NRG + Bluesky" / "Search Bluesky only" tab
  strip on the search page, mirroring the Feed tab strip.

### Week 4 (May 25–31): Practice tracker — chart-v2 calibration

The chart-v2 personalisation engine is heuristic; needs 4 more Jovian
Archive fixtures to calibrate. Per the deferred list.

- Pull 4 more public HD profiles with known type/authority/sun-gate
  combinations.
- Re-score against current heuristic, tune thresholds.
- Add a small "Why these?" disclosure under "Your domains" / "Teachers
  aligned" sections so users see the input → output reasoning.

### Week 5 (Jun 1–7): Practice tracker — group practice rooms (read-only)

Currently practice is private (RLS-locked). Members have asked for
"who else is practising right now" without it becoming a leaderboard.

- New table `practice_rooms` (migration 018a): topic_slug, name, member
  count (denormalised). RLS allows public read of room metadata, only
  members can join.
- New `practice_logs.room_id` (nullable) lets a logger optionally
  associate their session with a room. The room shows ANONYMOUS
  presence ("3 people are practising meditation right now") — never
  names.
- /my-frqncy/practice/ adds a "Sit with the network" panel showing
  active rooms. Click joins (sets room_id on next log). Voice: presence,
  not performance.

### Week 6 (Jun 8–14): Member-only Word Illuminator personalisation

The illuminator returns the same illumination for every member today.
Members should optionally get an illumination personalised to their HD
chart (when they've shared one).

- Add `chart_summary` (HD type, authority, primary domains) to the
  request payload when present.
- Adjust the prompt to weight the `practice_invitation` toward
  authority-matched practices (e.g. "wait for clarity" for Projectors).
- Voice: still suggestion not prescription. "An invitation that meets
  your design" not "your perfect practice".

### Week 7 (Jun 15–21): Federated feed — image embeds (Bluesky v1.3a)

The Bluesky reader (FederatedFeed + BlueskyReplies) renders text only
today. v1.3 of the timeline reader proposal (image grid 1×/2×/3×/4×).

- CSS-only image grid matching bsky.app's layouts.
- No lightbox in this round (CSS-only constraint).
- Falls back gracefully when `embed.images` is absent.

### Week 8 (Jun 22–28): NRG-native polish + handoff buffer

- Bookmarks panel on profile (`/social/profile/bookmarks/`) — surfaces
  what the user has saved across NRG + Bluesky cross-posts.
- Mention notifications panel — `notifications` table already exists;
  needs a UI surface beyond the in-Nav badge.
- Whatever surface friction has shown up in the first 7 weeks of real
  traffic.

## Track 3: Onchain identity + reputation (Weeks 3–10)

Per the user-selected scope: "Read-only surface first, hold bonded-invite
affordance until June after we've watched real usage".

### Week 3 (May 18–24, parallel with Track 2): Privy + Ethos auth spike

Per the risk flag in PROTOCOL-LESSONS-2026-05.md.

- 30-min spike: does our existing Privy app's token authenticate against
  Ethos's API? Or do we need to register separately?
- Document the answer + path forward in
  `proposals/ETHOS-INTEGRATION-V0.md`.

### Week 4–5 (May 25–Jun 7): Ethos read-only profile surface

- Migration 018b: `profiles.ethos_profile_id text` (nullable).
- New `social-src/src/lib/ethos-bridge.ts`:
  - `fetchEthosProfile(addressOrEthosId)` returns
    `{exists, vouchesReceived, invitedBy, profileUrl}`. **Score
    explicitly excluded.**
  - Per-session cache, public-API only (no auth).
- New `social-src/src/components/EthosPanel.tsx` — slot into the existing
  identity card on `/social/profile/<username>`. Renders:
  - "X vouches received on Ethos ↗" (no sum, no count compared to
    others)
  - "Invited by @username · bonded on Ethos ↗" when both sides have
    Ethos profiles
  - Disclosure: "Ethos has its own conventions including a numeric score
    we don't surface inside FRQNCY. Click through to view their full
    profile on Ethos."

### Week 6 (Jun 8–14): ◊ Ethos-verified badge in PostCard

- Mirrors the existing `◊ verified` Ed25519 badge.
- Module-level cache keyed by author DID.
- Renders only when the author has any Ethos profile, regardless of
  score. Treats Ethos as a binary "this person also exists on a
  reputation layer" not a quality signal.

### Week 7–8 (Jun 15–28): Bonded-invite affordance on /membership/

- "Optionally bond this referral on Ethos →" link on the existing
  Acknowledgements panel.
- Walks the user through the on-chain transaction via the connected
  Privy embedded wallet.
- The NRG ref code still works as today; the Ethos bond is an extra
  layer.
- UI must be loud about the 90-day bonded period and the trade-off.
  Default off. Inviter-only consent.

### Week 9 (Jun 29–Jul 5): DID-based identity wrapper

The genuinely portable identity step. Right now `wallet_address` +
`signing_public_key` IS our portable identity, but it's not packaged in
a way other ATProto/Nostr clients can pick up.

- New endpoint `/.well-known/did.json/<username>` returning a `did:web`
  DID document with the user's signing public key + wallet address +
  link to /api/export.
- The user's DID becomes `did:web:frqncy.network:u:<username>`. Backed
  by the existing identity columns; no migration.
- This is the inflection where our signed-message mirror becomes
  trivially consumable by any DID-aware client. Cost: ~1 day. No chain
  transactions.

### Week 10 (Jul 6–12): Optional content-anchor (Merkle root → Base)

- Nightly script (joins the auto-grow workflow): compute a Merkle root
  of all signed posts in the previous 24h, post a transaction with the
  root + epoch timestamp + post count to Base.
- Surfaces a "Public timestamp ledger" link from `/about/` showing the
  on-chain anchor history.
- Voice: "anchor", not "blockchain", not "decentralisation". The
  property we care about is "nobody can rewrite history without the
  receipt being public".
- Conditionally ship: if Privy's wallet abstraction makes this trivial,
  do it. If it requires a separate operator-managed key, defer to Q3.

## What's deferred through this window (and why)

These are NOT abandoned — just outside this 84-day window per
`PROTOCOL-LESSONS-2026-05.md`.

- **Farcaster bridge** — defer to Q3 2026 / Q1 2027. Neynar acquisition
  changed the trust shape; one bridge done well > three half-built.
- **Lens bridge** — defer to Q1 2027 protocol-portability window. Lens's
  pivot to its own chain reduces the cross-protocol pluralism case.
- **Nostr publish bridge** — defer to Q3. Cheap to add (signed-message
  mirror is two steps from nostr-postable) but lower urgency than
  deepening Bluesky.
- **Mobile (Capacitor)** — defer to Q4. Web works on mobile via PWA;
  native shell adds maintenance cost without clear pull yet.
- **E2EE v2 forward secrecy (Signal-style double-ratchet)** — defer.
  Current sealed-box model is solid for the threat model we have.
- **OAuth + DPoP for Bluesky** — defer until @atproto/api OAuth helpers
  stabilise. App password works for now.
- **Personalisation v0.2** (harness MCP-aware queries) — defer to Q3.
  Heuristic v0 is good enough for the next 90 days.
- **Reply-count on-demand refresh from BlueskyReplies** — defer; the
  nightly refresh is good enough and avoids the service-role API
  surface.

## Risk register

In rough priority order:

1. **Track 1 slips beyond Week 1.** If migrations / env vars / Privy /
   Stripe take longer than 7 days, every other track slides. Mitigation:
   block calendar for the whole week; treat as the only priority.
2. **Ethos API auth surprise.** The Privy + Ethos auth spike (Week 3)
   could reveal we need a separate registration. Mitigation: read-only
   public surfaces work without auth; worst case is the bonded-invite
   affordance (Week 7) slides to Q3.
3. **Stripe webhook signature verification.** The WebCrypto HMAC code
   path is correct but un-load-tested. Mitigation: trigger 5+ test
   webhooks via the Stripe CLI in Week 1 day 4.
4. **DID document stability** (Week 9). `did:web:frqncy.network:u:<x>`
   only works if the .well-known endpoint stays at a stable URL forever.
   Mitigation: write the contract into NRG-LAUNCH-CHECKLIST.md as a
   non-negotiable.
5. **Member acquisition outpacing infra.** Unlikely at our current
   scale, but if Track 4 lands a viral moment, RLS + edge-cache config
   needs review.

## Definition of done for the 90-day window

By 2026-08-01, NRG should be:

- Live with all 17 migrations applied; chat / feed / DM / search /
  membership / referrals / Bluesky bridge all working in production.
- Surfacing Ethos read-only attestations on profiles + verified badge
  on posts.
- Publishing portable did:web identity documents at .well-known/did.
- Optionally anchoring content fingerprints to Base nightly.
- Hosting an active cohort of ~50–100 founding members with a healthy
  cross-post rate to Bluesky.
- Pulling at least 5 cross-protocol identity verifications (members who
  joined via Bluesky → linked Ethos → bonded an invite).

If we hit half of this we're winning. The window is intentionally
ambitious. Adjust on each weekly retro; the proposal is the spine, not
the cage.
