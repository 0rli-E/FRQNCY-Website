# Phase 4.4 run — Section anchors + WebPage hasPart on topic pages

Date: 2026-04-29

## What was done

Two passes:
1. **First pass:** added id attributes to `<h2>` elements inside `<main>` and `WebPage hasPart` schema where h2 sections existed. FRQNCY's topic pages mostly DON'T use h2 — they use `<section class="resource-block">` with h4 per resource — so this pass only landed on the 9 pages that had h2 sections.
2. **Second pass (this one):** added id attributes to every `<section class="resource-block ...">` inside main, derived from the first h-tag or first href slug inside that block. Also added the `WebPage` hasPart schema referencing the resource-block ids.

## Final counts (after both passes)

- **Topic pages scanned:** 174
- **h2 elements with ids:** 19
- **section.resource-block elements with ids:** 372
- **Pages with WebPage hasPart schema:** 148

## Why this matters

Now any AI engine or human can deep-link to a specific curated resource within a topic page:

```
https://frqncy.network/meditation/#becoming-supernatural-dr-joe-dispenza
https://frqncy.network/meditation/#waking-up-sam-harris
```

When ChatGPT or Perplexity quotes one of FRQNCY's curated picks, they can cite the precise resource. The `WebPage` `hasPart` schema exposes the section list to crawlers as structured data — they don't have to guess the anchor format.

## Limit observed

Topic pages have an explainer block + a list of resources. They don't have multiple top-level sections like a blog post would. So the citation surface is per-resource, not per-section-of-argument. That's the FRQNCY shape.
